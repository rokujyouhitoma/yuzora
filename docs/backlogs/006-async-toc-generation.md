# [ENH] 非同期処理による目次抽出および描画の高速化 (ID: 006)

## 1. 概要 / Summary
大容量の青空文庫テキストをロード・レンダリングする際の初期表示パフォーマンスを最優先とするため、目次（TOC）関連の処理を非同期化・遅延評価にします。
現在、大容量のテキストパース時や、スクロールに追従した目次ドロワー内の「現在位置（アクティブ見出し）」判定において、同期的な DOM 操作および `getBoundingClientRect()` の繰り返し呼び出し（レイアウトスラッシング）が発生し、描画スレッド（メインスレッド）をブロックするリスクがあります。
本要件では、初期表示のレンダリングタスクを最優先した後に目次データを非同期で処理する仕組みを確立します。

  - `updateProgress()` またはスクロール監視部（アクティブ見出し判定の非同期化）

## 3. 要件と技術的アプローチ / Requirements & Technical Approach
1. **初期ロード時の遅延評価**:
   - `parseAozoraText()` における見出しへの ID 割り当てはHTML生成時に同期で行いますが、目次構造データ（`currentTOC` 配列）の構築や、目次用 DOM リストの構築プロセスは、本文のレンダリング（DOM 挿入および初期スクロール補正）が完全に完了した後に、`setTimeout` や `requestIdleCallback` を利用して非同期的にバックグラウンド実行します。

2. **IntersectionObserver による非同期スクロール追従アクティブ判定**:
   - スクロールイベントごとに全見出しに対して `getBoundingClientRect()` を同期的に呼び出してアクティブ状態を判定する現行の仕組みを廃止します。
   - `IntersectionObserver` を導入し、ビューポート内に入った見出し要素を非同期かつブラウザ最適化スレッドで検知します。現在表示されている見出し（アクティブな章）の情報を非同期で更新し、目次ドロワーが閉じて動作している間は無駄な座標計算を行わないように設計します。

3. **DOMレンダリングのバッチ化**:
   - 目次ドロワー内の項目数が数百件に及ぶ大容量の書籍（例：「宮本武蔵」全巻等）の場合、目次ドロワーを開く瞬間にすべての `.toc-item` を一括で生成・追加すると jank（カクつき）が発生します。
   - `DocumentFragment` を使用したバッチ DOM 挿入、または `requestAnimationFrame` を用いて分割描画することで、ドロワー開閉アニメーションのスムーズさを維持します。

## 4. 完了条件 / Success Criteria (DoD)
- [ ] 大容量の書籍データ（1MB以上）をロードした際、目次の解析およびドロワー表示処理が原因で初期表示およびページめくり操作がフリーズしないこと。
- [ ] 目次ドロワーを開いた際のアニメーションがスムーズ（60FPS近く）に維持されること。
- [ ] スクロール中に `getBoundingClientRect()` が連打されず、`IntersectionObserver` 等により非同期に見出しの現在地判定が行われること。
- [ ] すべてのE2Eテストおよびユニットテストが正常にパスすること。
